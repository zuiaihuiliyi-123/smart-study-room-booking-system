## 3. 功能与回归测试

### 3.1 阶段 3/4：缺陷复现与修复

QA 阶段共执行 36 条专项用例，复现 9 个缺陷（P0×1、P1×6、P2×2），并记录 2 个观察项（Q4-01/Q4-02）；共 11 项问题随后按报告顺序全部完成修复或加固：

| 编号 | 问题 | 修复要点 |
|---|---|---|
| Q3-01/02 | 签到/取消/关闭房间并发竞态 | 条件更新 `UPDATE ... WHERE status=期望值`；关闭前锁定座位行并复核影响清单 |
| Q3-03 | 幂等重放重复发送“预约成功”消息 | `_create_once` 返回是否新建，仅新建时通知 |
| Q3-04 | 并发加入黑名单产生多条有效限制 | `active_user_id` 唯一约束 + 服务层 409 |
| Q3-05 | 自动限制到期后违约计数未清零 | 到期解除时 `violation_count=0`，阈值统计按最近一次解除重置 |
| Q3-06 | 无登出接口，旧 JWT 持续有效 | 新增登出，递增 `token_version`；前端同步清理 |
| Q3-07 | 登录无 IP 限流 | 数据库固定窗口限流（登录 10/分/IP、注册 5/分/IP） |
| Q3-08/09 | `available-seats` 未校验日期窗口与粒度 | 今日至 +7 天、5 分钟对齐校验 |
| Q4-01 | 生产环境未关闭接口文档 | `APP_ENV=production` 关闭 docs/openapi/redoc |
| Q4-02 | 登录锁定可被定向利用、失败计数无界增长 | 锁定按「学号 + IP」；计数保留 30 天定期清理 |

修复后全量回归通过；新增迁移 `b7c8d9e0f1a2`、`e8f9a0b1c2d3`，Alembic 单链。

## 6. 性能测试

### 6.1 环境与数据

- 独立 MySQL 8.0.21（3307）+ uvicorn 单 worker（8010），默认连接池 10+20
- 数据集：3 间自习室 / 300 座 / 200 学生 / 1790 预约 / 300 违约 / 500 审计
- 客户端与服务端同机（32 核），结果用于基线对比，不代表生产容量

### 6.2 结果

| 场景 | 并发 | RPS | P50 | P95 | 成功率 |
|---|---:|---:|---:|---:|---:|
| 选座可约查询 | 50 | 90.1 | 406ms | 632ms | 100% |
| 座位目录 | 50 | 109.8 | 279ms | 1.28s | 100% |
| 我的预约 | 50 | 110.3 | 301ms | 1.37s | 100% |
| 看板概览（缓存） | 30 | 143.7 | 119ms | 664ms | 100% |
| 看板分时段占用 | 10 | 36.2 | 272ms | 373ms | 100% |
| 审计日志 | 30 | 131.1 | 130ms | 739ms | 100% |
| 创建预约 | 20 | 28.0 | 659ms | 1.22s | 100% |
| 登录（Argon2） | 5 | 15.7 | 310ms | 369ms | 100% |

全程无 5xx、无超时、无数据错误。

10 并发对照：读接口 P95 均在 110ms 以内、RPS 120–173；并发升至 50 后吞吐不再增长、P95 上升约 8–15 倍，说明请求在进入数据库前已发生排队。

### 6.3 分析

1. 单 uvicorn worker + 默认连接池是读请求的主要限制；建议多 worker 并重新压测。
2. 看板分时段占用是最重查询（36 RPS / P50 272ms），建议缓存或按日预聚合；概览缓存有效但缺少 single-flight。
3. 写入 100% 成功，延迟主要来自事务、行锁、时段占位与通知；需补“热点座位抢订”测试。
4. 登录 15.7 RPS、P50 310ms，符合 Argon2 安全成本预期；多 IP 高并发需按 CPU 规划。

## 7. 缺陷与风险汇总

### 7.1 已修复

见 §3.1 的 9 个已复现缺陷与 2 个观察项，均已修复或加固；当前无未修复的 P0/P1 业务缺陷。

### 7.2 仍存在的风险（非本轮阻断项）

| 风险 | 等级 | 现状 | 建议 |
|---|---|---|---|
| 多 worker 下调度器重复执行 | P1 | 每个进程都会启动 APScheduler | Web worker 关闭调度，单独调度进程/数据库租约 |
| 无 CI/CD | P1 | 无 `.github/workflows` | 接入后端测试+覆盖率+前端检查+Playwright |
| 无 Docker/Nginx 交付 | P1 | 仅有 Windows `start.bat` | 补容器与反向代理配置，启用 `--proxy-headers` |
| 审计日志无保留策略 | P2 | 只增不清理 | 按 BR-012 保留 1 年，增加归档任务 |
| 令牌策略 | P2 | 120 分钟 JWT，浏览器存储 | 评估短期 Access + Refresh / HttpOnly Cookie |
| 校园 NAT 下 IP 限流/锁定 | P2 | 依赖真实 IP | 配置可信代理，避免误伤或锁定失效 |
| 前端包体 | P2 | Element Plus 全量引入 | 改按需引入 |
| 生产 MySQL 版本差异 | P2 | 测试用 8.0.21，开发 9.6 | 上线前按目标版本复验迁移与并发 |
| 前端 E2E 未进 CI | P2 | 有 Playwright 用例 | 纳入流水线，避免回归 |

## 8. 结论与建议

### 8.1 结论

- 功能、边界、并发、系统、白盒测试均通过；核心业务闭环在真实 MySQL 与真实浏览器下可用。
- 后端语句覆盖 97.0%、分支 91.3%；前端语句 93.79%、分支 84.66%，满足课程项目质量基线。
- 性能基线可支撑校内小规模试运行，但单 worker 在 50 并发读场景已出现明显排队，需按实际并发规划部署。

### 8.2 上线前检查清单

1. 多 worker 部署 + 调度器单实例；重新跑本报告性能场景。
2. 补 CI（后端测试/覆盖率、前端检查、Playwright、MySQL 并发）。
3. 补 Docker/Nginx/HTTPS/可信代理配置；部署前备份并执行迁移。
4. 审计日志归档/清理；确认数据保留期符合要求。
5. 评估令牌策略与安全响应头；完成一次安全专项。
6. 在独立压测机与目标 MySQL 版本上复测性能；补热点座位并发测试。
