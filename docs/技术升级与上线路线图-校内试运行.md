# 技术升级与上线路线图（校内试运行版）

> 项目：智慧自习室预约与管理系统 · 小组：惊蛰破阵曲  
> 版本：V1.0（2026-11-12）  
> 适用目标：**校内小范围真实试运行**，不是公网 SaaS  
> 读者：4 名开发者、课程验收老师、校内运维对接人

---

## 0. 目标与边界

### 0.1 上线定义

"上线"在本项目中指：

- 在**学校内网**部署一套可访问的服务；
- 面向 **1–2 间自习室、100–200 名真实学生**试运行；
- 管理员能真实处理预约、违约、投诉、场地关闭；
- 数据每日可备份、故障 30 分钟内可恢复、版本 10 分钟内可回滚。

### 0.2 规模假设

| 指标 | 试运行目标 | 说明 |
|---|---|---|
| 注册用户 | ≤ 2000 | 单校区 |
| 日活 | ≤ 500 | 考试周峰值 |
| 峰值并发 | ≤ 300 | 含看板 10 秒轮询 |
| 日预约量 | ≤ 3000 | 5 分钟粒度 |
| 服务时间 | 07:00–23:00 | 凌晨可维护 |
| 部署形态 | 单台 Linux VM（4C8G） | MySQL 同机或独立 |

> 超过上述规模再考虑读写分离、Redis、多实例；当前**不需要**。

### 0.3 本期不做

- 公网访问、CDN、多地域容灾；
- 短信/邮件/微信通知（需求范围外）；
- 校园统一身份认证 CAS/LDAP（可作为二期）；
- 微服务、消息队列、Kubernetes；
- 7×24 值班与秒级告警。

## 2. 上线阻断项（P0）

### P0-1 调度器与 Web 进程分离

现状：`backend/app/tasks/scheduler.py` 在 FastAPI lifespan 内启动 `BackgroundScheduler`；`start.bat` 为单进程 `--reload`。

风险：改为多 worker 或多实例后，自动违约、自动签退、黑名单到期、投诉关闭会重复执行。

要求：

- Web 进程设置 `SCHEDULER_ENABLED=false`；
- 调度器独立进程/容器；
- MySQL `GET_LOCK` 单实例锁兜底；
- 每次任务执行后更新心跳时间，`/health/ready` 可检查。

验收：双实例运行 24 小时，违约记录、站内消息零重复。

### P0-2 MySQL 真实一致性验证

现状：`backend/tests/conftest.py` 全部使用内存 SQLite。

风险：行锁、唯一约束错误码、死锁、REPEATABLE READ 行为与 MySQL 不同。

要求：

- 增加 MySQL 集成测试 profile（CI service 或 Testcontainers）；
- 并发用例覆盖：20/50 个请求抢同一座位、同一用户抢多个座位；
- 把 `IntegrityError`、MySQL 1213 死锁映射为业务 409 并重试。

验收：仅 1 条预约成功，其余 409；`reservation_slots` 无重复行。

### P0-3 生产部署形态

要求：

- 多阶段 Dockerfile：前端 `dist` + Nginx，后端 `uvicorn`（多 worker）；
- Docker Compose：`mysql` / `api` / `web` / `scheduler`；
- Nginx：history fallback、gzip、静态缓存、安全响应头、HTTPS；
- 环境分层：`backend/.env.production`、前端构建参数；
- CORS 白名单改为校内域名/IP。

验收：干净 VM 一条命令启动；刷新 `/admin/reservations` 不 404；HTTPS 可访问。

> 若学校只提供 Windows Server：用 NSSM 注册 API/Scheduler 服务，任务计划执行备份；仍建议优先申请 Linux VM。

### P0-4 健康检查与异常处理

要求：

- `/health/live`：进程存活；
- `/health/ready`：数据库 `SELECT 1` + Alembic 版本 + 调度心跳；
- 全局 `Exception` 处理器：生成 `request_id`、记录堆栈、返回统一 JSON、不泄露内部信息；
- 访问日志包含 `request_id`、用户 id（不记录令牌/密码）。

验收：停 MySQL 时 ready 返回 503；任意 500 可用 `request_id` 检索到日志。

### P0-5 限流与注册策略

要求：

- Nginx `limit_req` 覆盖 `/api/v1/auth/*`、`/api/v1/reservations`；
- 应用层对登录、注册、预约做补充限流；
- 校内上线默认**关闭公开注册**：`REGISTRATION_ENABLED=false`，由管理员导入账号；或使用 `REGISTRATION_WHITELIST` 学号白名单；
- 注册接口保留，但生产环境按上述配置关闭。

验收：1 分钟内 100 次登录返回 429；非白名单学号无法注册。

### P0-6 可观测性与告警

要求：

- JSON 结构化日志，统一字段：`time`、`level`、`request_id`、`user_id`、`path`、`status`、`duration_ms`；
- 慢查询日志（>200 ms）；
- 关键指标：预约成功率、409 冲突率、调度任务耗时/失败、DB 连接数、磁盘使用率；
- 告警渠道：校内 IM 群 / 邮件，至少覆盖"服务不可用、磁盘 >85%、调度心跳超 5 分钟、备份失败"。

验收：一次预约请求可从 Nginx → API → SQL 串起；人为停调度器 5 分钟内收到告警。

### P0-7 备份、恢复与回滚

要求：

- 每日全量 `mysqldump` + binlog（RPO ≤ 5 分钟）；
- 备份文件存放在**应用服务器之外**（NAS/另一台主机）；
- 每月至少一次恢复演练；
- 发布流程：迁移 → 后端 → 前端；保留上一版本镜像；
- 回滚脚本：镜像回退 + 迁移回退策略（禁止直接 `downgrade` 生产库，必要时用备份恢复）。

验收：从备份恢复到新库并跑通核心流程 ≤ 30 分钟；回滚 ≤ 10 分钟。

## 3. 校内环境专项检查

| 项目 | 要求 | 原因 |
|---|---|---|
| NTP | 服务器必须启用时间同步 | 签到窗口、违约判定全部依赖服务器时间 |
| 时区 | `Asia/Shanghai`，容器显式设置 `TZ` | 避免 UTC 容器导致时间错位 |
| 内网域名 | 使用学校域名或固定 IP | 便于 CORS、证书、学生访问 |
| HTTPS | 校内 CA 证书或受信任证书 | 保护学号、密码、手机号 |
| 数据库账号 | 只使用 `study_app`，禁止 root | 最小权限 |
| 管理员账号 | 每人独立账号，禁止共用 admin | 审计可追溯 |
| 学生隐私 | 上线前告知学生数据用途；管理端脱敏 | 个人信息保护 |
| 日志保留 | 90 天，禁止记录令牌/密码 | 审计与合规 |
| 磁盘 | 数据盘 ≥ 100 GB，监控 >85% 告警 | 日志与备份增长 |

## 4. 优化清单（P1）

### 4.1 后端与数据

- 明确 Service 层事务边界；统一 `IntegrityError` → 409；MySQL 死锁重试。
- `reservation_service.py`（544 行）可拆查询/命令两部分，接口不变。
- `dashboard_service.get_overview` 将当日 `IN_USE` 全量拉到 Python 循环，改为 SQL 时间条件 + `COUNT`。
- 看板 10 秒轮询加 5–10 秒服务端缓存或 ETag，降低考试周 QPS。
- 补索引：`reservations.created_at`、`reservation_slots.slot_start`；用 `EXPLAIN` 验证。
- 显式配置连接池：`pool_size`、`max_overflow`、`pool_timeout`。
- 统一时间口径：存 `Asia/Shanghai` 或 UTC + 本地展示，禁止混用。
- 调度任务补 `misfire_grace_time`、执行记录、失败重试。

### 4.2 前端

- 补 ESLint + Prettier + Vitest；核心工具函数与 store 先覆盖。
- Playwright 覆盖 5 条主流程：登录、预约、取消、签到/签退、管理员关闭场地。
- 打包优化：`manualChunks` 拆分 ECharts/Element Plus；ECharts 按需引入。
- 全局错误边界、离线提示、轮询切页取消。
- 拆分 `AuditLogView.vue`（415 行）、`UserManageView.vue`（369 行）。
- 学生端移动端适配；键盘操作与对比度。
- 用 OpenAPI 生成 TS 类型，减少手写漂移。

### 4.3 工程流程

- GitHub Actions：后端 pytest（含 MySQL service）、前端 type-check/build/lint、`alembic heads` 单头检查。
- 清理被 Git 跟踪的 `__pycache__/*.pyc`（当前 10 个）；补 `.dockerignore`。
- 版本号、CHANGELOG、发布检查单。
- 演示种子数据只在 demo profile 使用，生产库禁止 demo 账号。

## 8. 运维手册要点

| 场景 | 操作 |
|---|---|
| 日常启动 | `docker compose up -d`；确认 `/health/ready` |
| 发布 | 备份 → `alembic upgrade head` → 更新 api → 更新 web → 冒烟 |
| 回滚 | 切回上一镜像 → 必要时按备份恢复数据库 |
| 备份 | 每日全量 + binlog；校验文件大小与可恢复性 |
| 恢复 | 新库导入 → 改连接串 → 冒烟 → 切换流量 |
| 数据库不可用 | 查磁盘/连接数/慢查询；恢复服务后确认 `/health/ready` |
| 调度停摆 | 查心跳；重启 scheduler；确认无重复执行 |
| 登录异常 | 查登录锁定记录、NTP、JWT 配置 |
| 磁盘告警 | 清理旧日志/备份；扩容数据盘 |

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|

| 单机故障 | 服务中断 | 每日备份异机存放；30 分钟恢复预案 |
