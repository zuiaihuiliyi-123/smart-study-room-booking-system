## 第一部分：整体评价

**这是一个完成度远高于一般课程项目的系统。** 业务规则在服务端是"真实现"而非摆设：预约创建有幂等键去重、行锁、`(seat_id, slot_start)` 唯一约束与 SQLite 锁重试；签到窗口 `[s−15, s+15)` 严格校验；违约记录按"预约单 + 类型"幂等；违约与黑名单在同一事务原子落盘；定时任务共有 4 个（自动违约 1 min、自动结束 1 min、黑名单到期 10 min、投诉超时关闭 1 h），见 `backend/app/tasks/scheduler.py`。这些都做对了。

### 最值得肯定的三处

1. **业务正确性优先**：预约冲突区分 C3（座位被占）/ C4（用户自身重叠）并回传冲突详情，见 `backend/app/services/reservation_service.py`；前端选座页甚至处理了"默认时段撞上自己既有预约"并自动顺延，见 `frontend/src/utils/useSeatBooking.ts`。
2. **界面"会解释规则"**：取消 / 签到 / 违约的口径不是藏在文档里，而是直接写在按钮旁与提示里（`frontend/src/utils/useMyReservations.ts`），自习室管理页还专门用一段说明区分"启用状态"与"临时关闭"（`frontend/src/views/admin/RoomManageView.vue`）。
3. **设计系统一致**：`--ssr-*` 设计令牌、`PageHeader / FilterBar / EmptyState / LoadingBlock / StatusTag` 公共组件在各页复用，空 / 加载 / 失败三态基本齐全。

### 最突出的四类问题（按严重度）

1. **角色闭环断裂（已决策解决）**：教师用户（R-03）此前被路由进学生端、菜单与学生完全相同，但后端只放行 R-01，教师点击任何操作都是 403；且需求文档 §2.1 与 §4.1.1 对教师权限**自相矛盾**。**业务方已决策：直接取消教师角色（R-03）**，本系统只保留 R-01 学生用户、R-02 自习室管理员、R-04 系统管理员。**文档与代码均已按该决策同步**（见 2.2 与 DEC-01）。
2. **账户状态治理半闭环**：后端已有 `PATCH /users/{id}/account-status`（ST-044/045/046 停用 / 恢复），但前端**没有任何入口**；用户管理页只读、只导向黑名单，而黑名单只能产生「受限」不能产生「停用」。
3. **数据展示与真实口径脱节**：看板趋势图注写"按当日**创建**统计"，而后端 `dashboard_service.py` 已按 FR-051 改为按**状态流转**统计 —— 图注与实现相反，会误导管理员。
4. **若干"差一步"的闭环**：预约管理翻页不刷新、评价有后端接口无管理端页面（2026-11-06 已补只读评价管理页）、密码无任何修改入口（2026-11-06 已补自助改密）、消息 / 列表超 500 条静默截断。

### 总体评价

**演示可交付、业务逻辑可信；作为真实学校系统，还差"角色治理 + 账号治理 + 数据口径对齐"三块。**

| 维度 | 评级 | 依据 |
|---|---|---|
| 业务逻辑完整性 | **A- / B+** | 核心预约 / 签到 / 违约 / 黑名单闭环扎实；账户停用、评价未闭环（教师角色已决策取消） |
| 权限与角色设计 | **B** | 学生 / 管理员边界清晰；教师角色已决策取消、代码待同步；系统管理员处理合理 |
| 用户体验 | **B+** | 规则提示到位、三态齐全；缺日期筛选、缺密码修改、部分入口缺 |
| 视觉与一致性 | **A-** | 设计令牌统一、组件复用好、响应式有断点 |
| 异常与边界 | **B+** | 冲突 / 幂等 / 并发 / 失败保留旧数据处理到位；401 丢原路径、停用态文案误导 |
| 产品成熟度 | **B** | demo 级优秀；真实投入使用需补账号治理与运营能力 |

## 第二部分：分角色体验评审

### 2.1 学生端（R-01）

**主要场景**：找座位 → 预约 → 签到 → 签退 → 查看记录 / 违约 / 消息 / 投诉。

**做得好的**：

- 选座页三档响应式布局、座位矩阵按分区分组、可约数量提示、选中后抽屉展示逐条校验清单（`judgements`）—— 学生能清楚知道"为什么不能约"。
- 「我的预约」用状态页签 + 角标计数，行内按钮严格按状态 gating（`frontend/src/utils/useMyReservations.ts`），并明确告知"不足 30 分钟不能自行取消、不计违约"。
- 首页「今日预约卡」+ 快捷入口 + 未读消息摘要，高频操作一眼可达。
- 消息点击会标记已读并跳转对应列表并高亮（`focus` 参数贯穿）。

**问题与建议**：

| 问题 | 现有设计（文件） | 用户影响 | 建议 |
|---|---|---|---|
| **预约记录无法按日期 / 自习室筛选** | 后端 `backend/app/api/v1/reservations.py` **已支持** `reserve_date_from/to、room_id、seat_id`，但前端 `frontend/src/utils/useMyReservations.ts` 注释仍写"只支持 status/page/page_size"，页面因此没做筛选 | 预约多了以后只能一页页翻，找某天某馆的记录很慢 | 前端补日期范围 + 自习室筛选控件（后端零改动，低成本高收益） |
| **无法修改密码（已修复）** | 个人资料页"修改密码"按钮 `disabled`，提示"请联系管理员"（`frontend/src/views/student/ProfileView.vue`）；管理员也无个人信息页 | 用户忘记密码只能找管理员 / 信息中心，系统内无自助通道 | 已新增 `PATCH /users/me/password` 与修改密码弹窗；管理员个人资料页同步补齐；改密后旧令牌立即失效 |
| **消息列表超 500 条静默截断** | store 翻页取全量但 `maxPages=5×100`（`frontend/src/stores/message.ts`），类型筛选与分页均在前端做 | 长期使用者第 501 条起看不到，且"共 N 条"偏小 | 改为后端分页 + 服务端类型筛选；或至少提示"仅显示最近 500 条" |
| **"记住我"名不副实** | 勾选只缓存学号（`frontend/src/views/auth/LoginView.vue`），token 始终写 localStorage（`frontend/src/stores/auth.ts`） | 机房共用电脑：上一人关浏览器，下一人打开仍是其登录态，可冒名操作 | 未勾选时 token 存 sessionStorage；或公共机强提示退出 |
| **首次使用无显式引导** | 首页信息架构清晰但无"新用户引导卡" | 新用户需自行摸索 7 天 / 4 小时 / 每日 2 条限制 | 对无预约记录用户展示一次性规则卡 |
| **状态页签计数用 5 次请求** | `loadCounts` 并发发 5 个 `page_size=1` 查询（`frontend/src/utils/useMyReservations.ts`） | 每次进入页面多 5 个请求，数据量大时开销明显 | 后端提供按状态分组计数接口，一次返回 |

### 2.2 教师端（R-03）—— **已决策：取消该角色**

**决策（2026-11-05）**：**直接取消教师角色（R-03）**，系统角色收敛为三类：

| 角色编号 | 角色名称 | 本版定位 |
|---|---|---|
| R-01 | 学生用户 | 预约 / 签到签退 / 查询本人记录 / 评价 / 投诉 |
| R-02 | 自习室管理员 | 全部业务管理（资源、预约、违约、投诉、黑名单、看板） |
| R-04 | 系统管理员 | 本版无业务操作权限，仅未来"全局参数配置" |

> 编号 R-03 予以**退役保留、不再复用**（与 FR 编号预留的做法一致），避免打乱 R-04 及既有引用。**R-04 不重新编号**。

**此前的断裂现象（作为历史背景保留）**：

- 路由曾把教师放进学生端：`/student` 的 `meta.roles = ['学生用户','教师用户']`（`frontend/src/router/index.ts`）。
- 菜单曾注明"学生端菜单（含教师用户，路由守卫同组放行）"（`frontend/src/layouts/menu.ts`）。
- 后端 `require_booking_user` / `require_student` 只放行 R-01 —— 于是教师登录后看到"你好，X 同学 · 累计违约 N 次"，点任何操作都被 403。

**决策依据**：

1. 需求文档 §2.1 与 §4.1.1 对 R-03 权限自相矛盾，长期无法自洽；
2. REF-01 原始资料**从未提及教师角色**，R-03 本就是为推进分析而设的【假设】；
3. 学校场景中教师与学生同样到馆自习的需求可由"学生用户"角色承载，单列角色无独立业务价值。

## 第三部分：核心业务流程评审

### 3.1 预约创建（学生）—— ✅ 完整、健壮

`选座查询 → 逐条校验(judgements) → 提交(幂等键) → 服务端复校验 → 创建待使用 → 站内通知`。服务端在事务内 `with_for_update` 锁座位 / 用户行，再以唯一约束兜底；并发冲突回 409 并带冲突详情。

**判定：闭环，无缺口。** 唯一建议：前端缺日期 / 自习室筛选（见 2.1）。

### 3.2 签到 / 签退 / 超时违约 —— ✅ 完整

签到窗口 `[s−15, s+15)`，重复签到 409 不覆盖首次时间；签退仅"使用中"；未签到超 `s+15` 由 1 分钟扫描任务自动判违约（幂等）。

**判定：闭环。**

### 3.3 取消（四条路径）—— ✅ 完整且语义清晰

- 学生无损取消：距开始 ≥30 min，否则 `ST-029` 拒绝且不计违约；
- 超时用户不可自行取消（只能管理员强制取消）；
- 管理员强制取消：仅"待使用"，原因必填 + 审计；
- 场地关闭批量取消：见 3.5。

**判定：四条路径互斥清晰，是设计亮点。**

### 3.4 违约 → 黑名单 → 到期解除 —— ✅ 完整（本会话已修事务割裂）

违约记录按"预约单 + 类型"幂等；`restrict_if_threshold(commit=False)` 与违约记录、双审计同事务提交（`backend/app/services/violation_service.py`）；自动限制到期由 10 分钟任务解除，**手动加入的限制不自动解除**（`backend/app/tasks/blacklist_expiry.py`）。

**判定：闭环。**

### 3.5 场地临时关闭 —— ⚠️ 闭环但"临时"名不副实

`预览受影响清单 → 二次确认（expected_reservation_ids 校验清单未变） → 置座位停用 → 默认保留 / 可选批量取消 → 通知`。本会话已补"窗口外孤儿预约提示"（`notified_outside_window`）。但**座位是永久停用，不会自动恢复**，需管理员手动改回"可用"。页面已注明这一取舍。

**建议**：在座位管理页或关闭记录处提供"一键恢复本馆座位为可用"的便捷操作，降低"临时关闭变永久"的运维成本（本期可不引入关闭记录实体）。

### 3.6 投诉流程 —— ✅ 基本闭环（细节需进一步验证）

学生提交 → 管理员受理 / 驳回 / 处理 / 关闭 → 结果通过站内消息回传学生；另有 1 小时"投诉超时关闭"任务。

**判定：闭环。** 建议：新投诉对管理员无主动提醒（管理端无消息入口），管理员需主动刷新投诉页；若投诉量大，建议给管理员站内消息 / 角标。

### 3.7 评价流程 —— ⚠️ 半闭环

学生仅能对"已完成且未评价"的预约提交 1–5 星 + 文字（一单一评）。后端有管理员列表接口，**但无管理端页面**，评价无人消费。

**判定：半闭环，建议补管理端或明确不做。**

### 3.8 账户状态管理（正常 / 受限 / 停用）—— ❌ 断裂

- 正常 → 受限：走黑名单（有 UI）✅
- 正常 / 受限 → 停用：**无 UI**（后端有接口）❌
- 停用 → 正常：**无 UI** ❌

**判定：这是一个真实的功能缺口**，用户管理页的"停用"筛选因此成为死选项。建议优先补（后端已就绪，前端 1 个抽屉即可）。

### 3.9 学生注册 —— ⚠️ 无身份核验

自助注册仅校验学号唯一，任何人可抢注任意学号，致真实学生被"该学号已注册"挡在系统外（`backend/app/services/auth_service.py` 的 register）。

**建议**：导入学籍白名单核验，或改为"信息中心批量开户"，或注册后标"待核验"。

**1. 当前系统是否已达到可交付、可演示水平？**
