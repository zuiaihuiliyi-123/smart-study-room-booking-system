# 数据库本地开发与 Alembic 协作说明

> 适用方案：**方案 A——每人本地 MySQL + Alembic 迁移**
> 当前迁移 head：`6856f6769461`；迁移链：`b12719e4dd71`（initial schema）→ `a99b54ed5877`（字段与 CHECK 约束）→ `6856f6769461`（房间删除保护）
> 目标：每位组员都能独立建库、建表、启动；表结构变更通过迁移同步，不靠手工改表。  
> 当前完整表结构见 [`数据库表结构说明.md`](数据库表结构说明.md)。

## 1. 一句话原则

- 表结构只认 `backend/alembic/versions/*.py`，不要用 Navicat 等工具手工改表后再指望别人知道。
- `.env` 每人一份、只放本机，不提交 Git；仓库里只保留 `.env.example`。
- 迁移由**固定负责人**生成和审核，其他组员只执行 `alembic upgrade head`。
- 已经执行过的迁移不要再修改；有新增变化就新建一个 revision。
- 日常开发数据不共享；需要共享演示数据时再另建共享库（方案 B）。

## 2. 首次配置（每位组员）

### 2.1 安装并启动 MySQL

建议统一安装 **MySQL 8.4 LTS**。安装时记住 root 密码，并确认服务已启动：

```bash
mysql -u root -p -e "SELECT VERSION();"
```

如果 `mysql` 命令找不到，把 MySQL 的 `bin` 目录加入系统 `PATH`，或使用 MySQL 自带的命令行客户端。

### 2.2 创建数据库和应用账号

仓库已提供脚本：`backend/scripts/init_db.sql`。

1. 打开文件，把里面的 `CHANGE_ME_APP_PASSWORD` 全部替换成你自己的密码。
   - 建议生成随机密码：`openssl rand -hex 16`
   - 只含 `0-9a-f`，不会遇到 URL 转义问题。
2. 用 root 执行：

Git Bash：

```bash
cd backend
mysql -u root -p --default-character-set=utf8mb4 < scripts/init_db.sql
```

PowerShell：

```powershell
cd backend
Get-Content .\scripts\init_db.sql -Raw | mysql -u root -p --default-character-set=utf8mb4
```

脚本会创建：

- 数据库 `smart_study_room`（`utf8mb4` / `utf8mb4_unicode_ci`）
- 应用账号 `study_app`，同时允许 `localhost` 和 `127.0.0.1`
- 只授予 `smart_study_room.*` 权限，应用不使用 root

验证应用账号：

```bash
mysql -u study_app -p -h 127.0.0.1 -D smart_study_room \
  -e "SELECT DATABASE(), CURRENT_USER(), @@version;"
```

### 2.3 后端依赖与 `.env`

```bash
cd backend
python -m venv .venv
source .venv/Scripts/activate      # Git Bash；PowerShell 用 .venv\Scripts\Activate.ps1
pip install -r requirements.txt

cp .env.example .env
```

编辑 `backend/.env`，把数据库密码和 JWT 密钥换成自己的：

```env
DATABASE_URL=mysql+pymysql://study_app:<你的密码>@127.0.0.1:3306/smart_study_room?charset=utf8mb4
JWT_SECRET_KEY=<openssl rand -hex 32 生成>
```

注意：

- `.env` 已在 `.gitignore` 中，**不要提交**。
- 密码里如果包含 `@`、`:`、`/`、`?`、`#`、`%`，必须做 URL 编码；建议直接用十六进制随机密码。
- `DATABASE_URL` 不要加引号。

### 2.4 建表与演示账号

```bash
alembic current                 # 新库此时应为空
alembic upgrade head            # 执行全部迁移
alembic current                 # 应显示 6856f6769461 (head)
python -m scripts.seed          # admin/admin123、student/student123
```

验证表：

```bash
mysql -u study_app -p -h 127.0.0.1 -D smart_study_room -e "SHOW TABLES;"
```

启动后端：

```bash
uvicorn app.main:app --reload
```

- Swagger：<http://127.0.0.1:8000/docs>
- 健康检查：<http://127.0.0.1:8000/health>

## 3. 日常开发：每次开始写代码前

```bash
git pull
cd backend
alembic current
alembic upgrade head
```

判断方式：

- `alembic current` 显示 `6856f6769461 (head)`：没有新迁移，可以直接开发。
- 显示的不是 `head`，或者 `git pull` 拉到了新的 `alembic/versions/*.py`：执行 `alembic upgrade head`。
- 不要因为自己本地没表就重新执行 `alembic revision --autogenerate`。

## 4. 修改表结构：迁移负责人的流程

**同一时间只建议一个人生成迁移。** 建议固定由 D（平台/基础设施）或你本人负责。

### 4.1 标准步骤

```bash
# 1. 先同步代码和数据库
git pull
alembic upgrade head

# 2. 修改 app/models/ 下的 ORM 模型
#    例如给 Seat 增加 note 字段

# 3. 生成迁移（会对比 models 与当前数据库）
alembic revision --autogenerate -m "add seat note"

# 4. 打开新生成的 alembic/versions/xxxx_add_seat_note.py 逐行审核

# 5. 在本机执行
alembic upgrade head

# 6. 跑测试和漂移检查
pytest
alembic check
```

`alembic check` 应输出：

```text
No new upgrade operations detected.
```

如果它检测到差异，说明 models 和迁移不一致，需要补迁移或修正 models。

### 4.2 审核迁移文件时重点看

- 表名、字段名、类型、长度是否正确。
- `nullable`、默认值是否符合预期。
- 索引、唯一约束、外键是否生成。
- 已有数据是否需要数据迁移（`op.execute(...)`）；autogenerate 不会自动处理数据迁移。
- `downgrade()` 是否能安全回退；如果会丢数据，要在 PR 里说明。
- 是否混入了无关的表或字段变化；一个迁移只做一件事。

### 4.3 提交与通知

模型文件和迁移文件必须**在同一个 PR/提交**里：

```bash
git add app/models/... alembic/versions/xxxx_add_seat_note.py
git commit -m "feat(db): add seat note"
git push
```

合并后通知组员：

```text
数据库有新迁移，请执行：
git pull
cd backend
alembic upgrade head
```

## 5. 组员日常：只做这些

1. 安装 MySQL 8.4，按第 2 节建库、建账号、写自己的 `.env`。
2. 每次开始开发前执行：

   ```bash
   git pull
   cd backend
   alembic upgrade head
   ```

3. **不要**自己运行 `alembic revision --autogenerate`，除非迁移负责人明确安排。
4. **不要**修改已经执行过的迁移文件，也不要手工 `ALTER TABLE`。
5. 需要加字段/加表时，先提 Issue 或告诉迁移负责人，由负责人统一生成迁移。
6. 拉代码后如果启动报缺表/缺字段，先执行 `alembic upgrade head`，不要重建整个库。
7. 本地数据是可丢弃的；不要把自己的测试数据提交到仓库。
8. `.env` 不提交、不发群、不写进截图。

## 6. 常用 Alembic 命令

| 命令 | 用途 | 备注 |
|---|---|---|
| `alembic current` | 查看当前数据库版本 | 日常最常用 |
| `alembic history --verbose` | 查看迁移历史 | 确认基线和新迁移 |
| `alembic heads` | 查看是否有多个 head | 多人同时加迁移时检查 |
| `alembic upgrade head` | 应用全部未执行迁移 | 组员日常只需要这个 |
| `alembic revision --autogenerate -m "..."` | 根据 models 生成迁移 | 只由迁移负责人执行 |
| `alembic check` | 检查 models 与迁移是否漂移 | CI 和提交前执行 |
| `alembic downgrade -1` | 回退一个迁移 | 只在本机临时使用，共享库禁止 |
| `alembic stamp head` | 把数据库标记为最新 | 仅特殊场景；不要拿来掩盖迁移失败 |
| `alembic merge -m "merge heads" <rev1> <rev2>` | 合并多个 head | 尽量通过协调避免 |

## 7. 常见问题

### 7.1 `UnicodeDecodeError: 'gbk' codec can't decode ... alembic.ini`

Alembic 在 Windows 上按系统 locale 读取 `alembic.ini`。该文件里的注释必须保持 ASCII；不要往 `alembic.ini` 里加中文注释。

### 7.2 `Access denied` 或 `Host ... is not allowed`

- 确认 `study_app` 的 `localhost` 和 `127.0.0.1` 两个主机名都已创建。
- 检查 `.env` 里的密码是否和创建账号时一致。
- 密码含特殊字符时，检查是否做了 URL 编码。
- 如果连接的是别的机器，需要创建对应网段的账号（方案 B）。

### 7.3 `Table ... already exists` / 数据库里没有 `alembic_version`

说明数据库是手工建过表、或旧的残留库。推荐在本机直接重建：

```bash
mysql -u root -p -e "DROP DATABASE smart_study_room;"
mysql -u root -p --default-character-set=utf8mb4 < scripts/init_db.sql
cd backend
alembic upgrade head
python -m scripts.seed
```

只有确认现有表结构和迁移完全一致时，才考虑 `alembic stamp head`；否则会掩盖差异。

### 7.4 `Target database is not up to date`

```bash
alembic upgrade head
```

### 7.5 出现了多个 head

```bash
alembic heads
alembic merge -m "merge heads" <rev1> <rev2>
alembic upgrade head
```

然后提交合并迁移。最好还是避免两个人同时生成迁移。

### 7.6 MySQL 版本不一致

团队建议统一 **MySQL 8.4 LTS**。当前本机 9.6 已验证可用，但不要长期出现“有人 8.4、有人 9.6、有人 8.0”的混用；如果出现兼容问题，优先用 Docker 固定 8.4。

### 7.7 seed 输出中文乱码

Git Bash 下可以加：

```bash
PYTHONIOENCODING=utf-8 python -m scripts.seed
```

不影响数据写入。

### 7.8 `alembic.ini` 里的 `sqlalchemy.url` 要不要改？

不需要。`alembic/env.py` 会用 `app.core.config.settings.database_url` 覆盖它，实际连接串来自 `backend/.env`。`alembic.ini` 里的 root/password 只是占位。

## 8. 你（项目负责人/迁移负责人）要做什么

- 维护 `backend/.env.example`、`backend/scripts/init_db.sql` 和本文档。
- 固定迁移负责人；同一时间只让一个人生成迁移。
- 每次模型变更：生成迁移 → 审核 → 本机 upgrade → `pytest` → `alembic check` → 提交模型+迁移。
- 合并迁移 PR 后通知组员执行 `git pull` + `alembic upgrade head`。
- 保持 `alembic.ini` 为 ASCII，避免 Windows GBK 解码问题。
- 不要把 root 密码、`.env` 或自己的 `study_app` 密码发到群里/仓库。
- 需要共享演示环境时，另建共享 MySQL 和独立账号，不要让大家连你的开发机。
- 可选：在 CI 中起一个 MySQL 8.4 service，执行 `alembic upgrade head`、`alembic check`、`pytest`。

## 9. 组员要做什么

- 按第 2 节完成本机 MySQL、`.env`、venv、迁移、seed。
- 每天开发前 `git pull` + `alembic upgrade head`。
- 不生成迁移、不改已执行迁移、不手工改表。
- 需要表结构变更时找迁移负责人，不自己 `autogenerate`。
- 遇到迁移失败，提供：`alembic current`、`alembic heads`、完整报错、MySQL 版本；不要先删 `alembic_version` 或重建共享库。
- 本地库可以随时重建；共享库/演示库不要随意 drop。

## 11. 数据共享补充

方案 A 不共享数据，每个人本地库互相独立。如果演示时需要同一份数据：

- 优先扩展 `backend/scripts/seed.py`，让每位组员执行同一套初始化数据；
- 临时共享可用 `mysqldump` 只导出数据，但**表结构仍然以 Alembic 为准**；
- 不要把所有人的 `.env` 指向某一个人的笔记本；需要共享库时按方案 B 单独搭 MySQL。
