# 智慧自习室预约与管理系统 · 性能测试报告

| 项目 | 内容 |
|---|---|
| 测试日期 | 2026-11-26 |
| 测试类型 | API 基线性能测试（真实 MySQL + 真实后端，asyncio 并发压测） |
| 代码基线 | `main` 分支当前工作区 |
| 测试环境 | 独立 MySQL 8.0.21（3307）、后端 8010；未使用开发库与 8000 服务 |
| 压测工具 | Python 3.13 + `httpx.AsyncClient`（仓库自带脚本，无额外依赖） |
| 结论 | 单 worker 基线可支撑约 90–170 RPS 的读请求；高并发下延迟明显上升，未出现错误；登录受 Argon2 限制约 15 RPS |

> 客户端与服务端运行在同一台 32 核 Windows 机器上，本文结果用于**基线对比与瓶颈定位**，不等同于生产容量结论。

---

## 1. 测试目标

1. 测量学生端核心读取链路（选座、座位目录、我的预约）的吞吐与延迟。
2. 测量管理端看板、审计列表的响应能力，验证 10 秒缓存效果。
3. 测量预约写入路径在真实事务、行锁、时段占位、通知下的表现。
4. 测量登录（Argon2）成本。
5. 在高并发下确认是否出现 5xx、超时或数据错误。

## 4. 测试结果

### 4.1 主结果

| 场景 | 并发 | 请求数 | RPS | 平均 ms | P50 | P95 | P99 | 成功率 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 选座可约查询 | 50 | 1838 | 90.1 | 551.2 | 406.5 | 631.8 | 5526.2* | 100% |
| 座位目录 | 50 | 2224 | 109.8 | 452.1 | 278.9 | 1283.5 | 1990.6 | 100% |
| 我的预约 | 50 | 2236 | 110.3 | 449.9 | 300.8 | 1370.3 | 2043.3 | 100% |
| 看板概览（缓存） | 30 | 2895 | 143.7 | 208.0 | 119.0 | 664.1 | 1064.6 | 100% |
| 看板分时段占用 | 10 | 550 | 36.2 | 275.4 | 272.4 | 372.9 | 414.2 | 100% |
| 审计日志 | 30 | 1993 | 131.1 | 227.4 | 130.1 | 739.2 | 1047.6 | 100% |
| 创建预约 | 20 | 100 | 28.0 | 702.9 | 659.2 | 1216.1 | 1221.4 | 100% |
| 登录 | 5 | 160 | 15.7 | 316.6 | 310.4 | 368.8 | 389.5 | 100% |

\* 首个场景出现一次约 5.5 秒的 P99 离群值；预热后复测同一场景 P99 降至约 1.08 秒，判断为冷启动/连接建立影响。

全程无 5xx、无超时、无 429（登录限流已调高）、无数据错误。

### 4.2 低并发对照（10 并发，10 秒）

| 场景 | 10 并发 RPS | P50 | P95 | 50 并发 RPS | 50 并发 P95 |
|---|---:|---:|---:|---:|---:|
| 选座可约查询 | 119.7 | 80.9ms | 110.5ms | 90.1 | 631.8ms |
| 座位目录 | 172.9 | 55.5ms | 85.1ms | 109.8 | 1283.5ms |
| 我的预约 | 170.0 | 56.3ms | 80.5ms | 110.3 | 1370.3ms |

结论：**低并发下延迟很低，但并发升到 50 后吞吐不再增长、P95 上升约 8–15 倍**，说明请求在进入数据库前已发生排队。

## 5. 结果分析

### 5.1 读取链路

- 10 并发时 P95 均在 110ms 以内，单请求性能可以接受。
- 50 并发时吞吐停留在 90–110 RPS，延迟主要来自排队而非 SQL 本身。
- 当前为 **单 uvicorn worker + 默认连接池（10+20）**。50 并发时：
  - FastAPI 同步端点在线程池中执行；
  - 数据库连接最多 30 个，其余请求等待；
  - 单进程的 Python/SQLAlchemy 处理能力成为上限之一。
- 提高到多 worker + 按 worker 调整连接池，是下一步最直接的扩容手段。

### 5.2 看板

- 概览接口带 10 秒进程内缓存，30 并发下 RPS 最高（143.7），说明缓存有效。
- 但复测时同一场景 RPS 降到 68.5、P95 升到 869.7ms，说明结果对启动时缓存是否命中、并发是否同时击穿较敏感；缓存没有 single-flight，冷启动瞬间可能出现多个重查询。
- 分时段占用（`group_by=slot`）无缓存，10 并发仅 36 RPS、P50 272ms，是管理端最重的查询。数据量为 300 座 × 7 天，已明显高于概览。

### 5.3 写入链路

- 100 次不同用户/座位的创建预约全部成功，20 并发下 28 RPS、P95 1.2s。
- 单次写入包含：座位/用户行锁、C1～C6 校验、预约单插入、24 行时段占位、提交、刷新、站内消息。延迟高于读接口符合预期。
- 当前测试没有制造热点座位冲突，未覆盖极端锁竞争场景（并发抢同一座位）。

### 5.4 登录

- 5 并发下 15.7 RPS，P50 310ms，主要成本是 Argon2 校验，属于安全设计的预期开销。
- 生产默认登录限流为 10 次/分/IP，因此单 IP 的实际登录吞吐远低于此；该结果用于评估多 IP 同时登录时的 CPU 成本。
- 多 worker 部署时登录会并行使用多核，但需注意 CPU 与数据库连接预算。

## 6. 发现与建议

### 6.1 优先建议

1. **多 worker 部署并重新压测**
   当前单 worker 在 50 并发下已出现明显排队。建议用 2～4 个 uvicorn worker，按 `总连接数 = worker 数 × (pool_size + max_overflow)` 控制 MySQL 连接，并重新跑本报告场景。
2. **看板分时段占用增加缓存或预聚合**
   `dashboard/seat-usage?group_by=slot` 是当前最重接口（36 RPS / P50 272ms）。可按 10 秒 TTL 缓存，或按日预聚合到统计表；概览缓存建议加 single-flight（同一 key 只允许一个请求回源）。
3. **写入路径专项压热点**
   本轮是“100 个不同座位”的温和写入。考试周真实峰值更可能是多人抢同一时段/同一座位，需要单独做热点座位并发测试，观察行锁等待与 409 比例。
4. **登录容量按 CPU 规划**
   Argon2 是故意保留的成本。多 IP 高并发登录会占满 CPU；建议在网关层保留登录限流，并监控 CPU 使用率。

### 6.2 其他建议

- 将性能测试纳入发布前检查：至少跑 10 并发与 50 并发两档，记录 P95、错误率。
- 在独立压测机上执行，避免客户端与服务端争用同一 32 核机器。
- 开启 MySQL 慢查询日志与应用 APM，定位单条 SQL 与锁等待。
- 对 `available-seats`、看板查询持续观察执行计划，数据量增长后确认索引仍被使用。
- 若引入多 worker，调度器只保留一个进程运行，避免重复扫描。

## 7. 局限性

1. 客户端与服务端同机，压测客户端本身也消耗 CPU，结果偏低或波动。
2. 仅测试短时 10–20 秒场景，没有做 1 小时以上稳定性/内存泄漏测试。
3. 数据库为 MySQL 8.0.21，开发环境为 MySQL 9.6；生产版本与参数需复验。
4. 数据集规模有限（300 座、1790 张预约），未达到多年历史数据量。
5. 未测试浏览器端渲染性能、首屏加载、Lighthouse 指标。
6. 未测试网络延迟、反向代理、HTTPS 终止等真实链路成本。

## 8. 复现方式

```bash
# 1. 隔离 MySQL（3307）与空库 ssr_perf，执行迁移
cd backend
DATABASE_URL="mysql+pymysql://root:@127.0.0.1:3307/ssr_perf?charset=utf8mb4" \
  .venv/Scripts/alembic.exe upgrade head

# 2. 生成性能数据与上下文
DATABASE_URL="..." .venv/Scripts/python.exe -m tests.performance.seed_perf \
  --context ".perf/context.json"

# 3. 启动后端（关闭调度器；压测登录时临时调高限流）
DATABASE_URL="..." APP_ENV=production SCHEDULER_ENABLED=false \
  LOGIN_RATE_LIMIT_PER_MINUTE=100000 REGISTER_RATE_LIMIT_PER_MINUTE=100000 \
  .venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8010

# 4. 运行压测
.venv/Scripts/python.exe -m tests.performance.load_test \
  --context .perf/context.json --out .perf/results.json
```
